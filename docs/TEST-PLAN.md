## 1. Принципы

1. **Доказательство = отчёт с устройства.** Каждый вывод «прошло / не прошло» на телефоне подкрепляется файлом отчёта (§6.5): логи, `device.json`, CSV производительности. Слова «вроде работает» не считаются.
2. **adb не нужен.** Всё, что требуется от Андрея: установить APK, запустить сценарий кнопкой, нажать «Отправить отчёт» и переслать файл. adb через ПК Андрея используем позже, только с его согласия (PLAN §2).
3. **Эталон решает.** Критерии Э1 принимаются на Pixel 8 Pro. Остальные устройства дают блокеры (ярусы 1a/1b), но не принимают критерии.
4. **Детерминированные сценарии.** Замеры делаем только встроенными сценариями (§5) с фиксированной картой, сидом, камерой и настройками. Ручная игра нужна для поиска багов, но не для цифр.
5. **Файлы EA не покидают устройство Андрея и бокс** (TEAM.md, ADR-0001 §3.6). Отчёт не содержит `.big` и ресурсов игры (§6.6). Скриншоты игры храним на боксе вне git (`/workspace/bfme-mobile/qa-artifacts/`), в git (`tests/reports/`) кладём только текст и цифры.

## 3. Серьёзность дефектов

### 3.1 Что считаем падением
**Падение** — любое завершение процесса игры, которое не инициировал пользователь (кнопка «Выход», смахивание из списка недавних) и система не сделала штатно в фоне:

| Тип | Как узнаём без adb |
|---|---|
| Нативный сигнал: **SIGSEGV, SIGBUS, SIGABRT** (в том числе `abort()`, `DEBUG_CRASH`, `std::terminate`), **SIGILL, SIGFPE, SIGTRAP** | обработчик сигналов форка (`crash.log`), `ApplicationExitInfo` `REASON_CRASH_NATIVE` + tombstone (Android 12+) |
| Необработанное исключение Java/Kotlin (лаунчер, SDLActivity) | `UncaughtExceptionHandler` → файл; `REASON_CRASH` |
| **ANR** (диалог «Приложение не отвечает» или убийство системой) | `REASON_ANR` + трассы потоков (Android 11+) |
| **Убийство из-за памяти на переднем плане** (LMK/OOM) | `REASON_LOW_MEMORY`, или `REASON_SIGNALED` с SIGKILL при importance = foreground; последняя запись кольцевого лога без штатного завершения |
| **Потеря GPU** с выходом: `EGL_CONTEXT_LOST` на `eglSwapBuffers`, `glGetGraphicsResetStatus` ≠ `GL_NO_ERROR`, `VK_ERROR_DEVICE_LOST`, краш внутри `libGLES_mali.so` или драйвера PowerVR | событие `gpu_lost` в кольцевом логе; бэктрейс в драйвере в tombstone |
| **Самоубийство по сторожу зависаний** (§6.2) | запись `hang` в `crash.log` |
| Выход по `REASON_EXCESSIVE_RESOURCE_USAGE`, `REASON_INITIALIZATION_FAILURE` | `ApplicationExitInfo` |

**Не падение:** система выгрузила процесс в фоне (`REASON_LOW_MEMORY` при importance ≥ cached), обновление приложения, принудительная остановка пользователем. Но если после возврата игра не восстановилась корректно (не вернулась в меню, потеряла настройки), это **major** (ошибка жизненного цикла).

**Зависание** — нет нового кадра на переднем плане **≥ 5 с** вне экрана загрузки, или на экране загрузки ≥ 30 с нет продвижения прогресса **[предложение QA]**. **Фриз** — один кадр дольше 1 с во время игры.

### 3.2 Классы
- **Блокер**: сборка не уходит Андрею как кандидат, веха не закрывается, исправляем до всего остального.
- **Major (серьёзный)**: исправляем в текущей вехе, кандидат возможен с известным списком.
- **Minor**: исправляем по возможности, в отчёте вехи упоминаем.
- **Trivial**: косметика, бэклог.

## 5. Методика: детерминированный прогон загрузки, FPS и память на Pixel 8 Pro

### 5.1 Как запускаются сценарии без adb
- **Кнопка в лаунчере** «Тесты QA» (видна в сборках для своих) со списком сценариев: `load-run`, `perf-run`, `soak-10m`, `gpu-synthetic`, `crash-selftest`. **[предложение QA, реализует А]**
- Тот же механизм, что у форка для диагностики: **файл-маркер** в каталоге игры (в форке `gx_perf.txt`, `gx_trace.txt`, их переключает экран SetupActivity). Наш файл: `files/qa/autotest.json` с параметрами сценария. Есть файл — лаунчер стартует сценарий.
- **Firebase Test Lab Game Loop**: интент `com.google.intent.action.TEST_LOOP` с номером сценария, результат пишется в URI из `getIntent().getData()` (https://firebase.google.com/docs/test-lab/android/game-loop). Так же можно запускать сценарии и локально. Только для сценариев без данных EA (`gpu-synthetic`, `crash-selftest`).
- Движку сценарий передаётся аргументами командной строки, как у форка в `GeneralsZHActivity` (`-gxFastTo`, `-gxAutoQuit`). Наши аргументы: `-qaScenario <name> -qaOut <dir> -seed <N>` **[предложение QA, точки входа согласует Л]**.

### 5.2 load-run: детерминированный прогон загрузки
**Цель:** одинаковый путь загрузки на каждом запуске; время каждой стадии; проверка, что загрузка детерминирована (CRC); скриншоты для проверки магенты.

Фиксируем: карта M1 (`map mp fords of isen`, E1-BACKLOG), 2 игрока-заглушки, сид `-seed 1`, бэкенд GLES, масштаб 756p, 30 FPS-кап, звук по умолчанию, язык, `Options.ini` из сценария (копия сохраняется в отчёт). Ввод пользователя игнорируется до конца сценария.

Шаги и метки времени (монотонные часы, мс от старта процесса; движок пишет `stage,t_ms` в `perf/stages.csv`):
1. `process_start` (по `Process.getStartUptimeMillis()`, API 24+);
2. `launcher_ready` → `engine_main` → `vfs_mounted` (число архивов и записей) → `ini_parsed` (число файлов, ошибок) → `map_loaded` → `first_frame` → `in_game`;
3. **CRC загрузки:** `TheGlobalData->m_iniCRC` (CRC INI, уже есть в движке и пишется в заголовок реплея), `GameLogic::getCRC(CRC_RECALC)` на логическом кадре 1 и 30, хеш списка смонтированных файлов VFS (имя, размер, SHA-256 из манифеста импорта);
4. **камера по маршруту**: 5 контрольных точек, переход привязан к **номеру кадра логики**, а не к реальному времени. В каждой точке ждём 2 с, делаем скриншот (`glReadPixels` с фреймбуфера в PNG) и считаем пиксели `#FF00FF` (±2 по каналам);
5. выход и запись `qa/result.json` (`status`, стадии, CRC, счётчики магенты, предупреждения).

**Холодный запуск:** первый запуск после перезагрузки телефона или «Остановить» в настройках. Приложение отмечает тёплый или холодный старт в `result.json` (по `ApplicationExitInfo` прошлого выхода и наличию кэша шейдеров).

**Прошло, если:** 3 прогона подряд со `status=ok`; CRC (`iniCRC`, CRC кадров 1 и 30, хеш VFS) **одинаковые во всех прогонах**; 0 пикселей магенты; разброс времени `map_loaded` ≤ 15% между тёплыми прогонами **[оценка]**. Время загрузки карты и триггер ETC2 (> 30 с) берём из медианы тёплых прогонов.

### 5.3 perf-run: FPS и время кадра
- Та же карта и настройки, что в load-run. После `in_game` **прогрев 60 с**, затем **замер 300 с** по повторяемому маршруту камеры (облёт базы, приближение к воде и лесу, максимальное отдаление). Для нагрева есть вариант `soak-10m`: тот же маршрут по кругу 600 с.
- **Что пишем в `perf/frames.csv`** (одна строка на кадр, буфер в памяти, сброс на диск раз в секунду в отдельном потоке):

| Колонка | Смысл |
|---|---|
| `frame` | номер кадра рендера |
| `logic_frame` | номер кадра логики |
| `t_ns` | `CLOCK_MONOTONIC` в начале кадра |
| `present_interval_ms` | интервал между соседними `eglSwapBuffers`/подачей Swappy. **Главная метрика плавности** |
| `cpu_frame_ms` | время работы кадра на CPU (от начала `GameEngine::update` до вызова swap), то есть запас до 33,3 мс |
| `logic_ms`, `client_ms` | разбивка по подсистемам. В форке уже есть `[GX-PERF]` с агрегатом раз в секунду (`GameEngine.cpp`, маркер `gx_perf.txt`). Предлагаем писать то же самое покадрово в CSV |
| `gpu_ms` | время GPU по `GL_EXT_disjoint_timer_query`, если расширение есть **[не проверено на Mali-G715]**, иначе пусто |
| `swappy_late` | кадр пропустил vsync-слот (по статистике Swappy, если доступна) |

- Если доступно `EGL_ANDROID_get_frame_timestamps`, дополнительно пишем фактическое время показа (`EGL_DISPLAY_PRESENT_TIME_ANDROID`) **[не проверено на Pixel 8 Pro]**.
- **Цена CRC каждый кадр** (просьба NET-DESIGN §3.2): дополнительный perf-run с `-gxCrcEveryFrame` (или `-gxCrcLog`, `docs/REPLAY-TESTS.md` §8); разница p50/p95 `logic_ms` с обычным прогоном = стоимость `getCRC(CRC_RECALC)` на Pixel 8 Pro.
- **Внутриигровой оверлей** (часть E1-39): FPS, график времени кадра за 5 с, `cpu_frame_ms`, RSS/PSS, тепловой статус, масштаб и бэкенд. Включается в настройках или жестом. На скриншотах для отчёта он виден, в замерах FPS его стоимость учитываем: perf-run идёт **без оверлея**, отдельный прогон с оверлеем показывает его цену.

### 5.4 Метрики и правила для критерия Э1-3
Целевой интервал **T = 33,33 мс** (30 FPS-кап, ADR-0002 §7). Считаем по `present_interval_ms` за 300 с замера:

| Метрика | Определение | Порог для Э1-3 (Pixel 8 Pro, 756p, GLES) |
|---|---|---|
| Средний FPS | число кадров / длительность | **≥ 29,5** |
| p50 / p95 / p99 интервала | перцентили | p50 ≤ 34,0 мс; **p95 ≤ 36,0 мс**; p99 — фиксируем |
| FPS p1 (1% low) | 1000 / p99 | фиксируем (как в ADR-0002 §10) |
| **Jank %** | доля кадров с интервалом > 1,5·T (> 50 мс) | **≤ 2%** |
| Big jank | интервалы > 100 мс | ≤ 5 за 300 с |
| Фриз | интервалы > 250 мс вне загрузки | **0** |
| Запас CPU | p95 `cpu_frame_ms` | фиксируем; > 30 мс означает, что запаса нет (риск для Э2 с юнитами) |

Пороги — **[предложение QA]**, утверждает Лид. На 100% High и натив 2992×1344 те же метрики фиксируем без требования «прошло».

### 5.5 Память без adb
`dumpsys meminfo` (E1-41) требует adb. Без adb используем API своего процесса:

| Метрика | Источник | Частота |
|---|---|---|
| RSS, пик RSS | `/proc/self/statm`, `VmHWM` из `/proc/self/status` (дёшево, из нативного кода) | 1 с |
| **PSS всего**, Graphics, Native Heap, Code, GL | `Debug.getMemoryInfo()` → `getTotalPss()`, `getMemoryStat("summary.graphics")`, `"summary.native-heap"`, `"summary.code"` (Java, только свой процесс) | раз в 30 с **в отдельном потоке**, плюс на каждой стадии load-run. Вызов дорогой (разбор smaps): в perf-run его время пишем в лог, чтобы отделить от рывков |
| PSS по smaps_rollup | `/proc/self/smaps_rollup` (дешевле полного smaps) | 10 с, если читается **[проверить на Pixel 8 Pro]** |
| Давление памяти системы | `ActivityManager.getMemoryInfo()` (`availMem`, `lowMemory`, `threshold`), колбэки `onTrimMemory` | 5 с и по событию |
| Нативная куча | `mallinfo()` (bionic) | 10 с |

`ActivityManager.getProcessMemoryInfo()` для частых замеров не годится: начиная с Android 10 он ограничен по частоте и отдаёт кэш **[не проверено в этой сессии]**. Всё пишем в `perf/samples.csv`. **Прошло** для Э1: пик PSS в perf-run в пределах бюджета ADR-0002 §8 и ни одного `onTrimMemory(RUNNING_CRITICAL)`. Для сверки один прогон с `dumpsys meminfo` через adb можно сделать позже с согласия Андрея.

### 5.6 Нагрев и троттлинг без adb
- `PowerManager.getCurrentThermalStatus()` и слушатель `OnThermalStatusChangedListener` (API 29): статус NONE…SHUTDOWN; каждое изменение пишем в `samples.csv` и кольцевой лог.
- `PowerManager.getThermalHeadroom(10)` (API 30): прогноз запаса до троттлинга, раз в 10 с (метод ограничен по частоте **[проверить]**).
- Температура батареи: `ACTION_BATTERY_CHANGED` → `EXTRA_TEMPERATURE` (десятые доли °C), раз в 10 с; там же уровень заряда и признак зарядки.
- Частоты CPU: `/sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq`, если SELinux разрешает чтение **[не проверено]**.
- **Как считаем троттлинг в soak-10m:** сравниваем первую и последнюю минуту: падение среднего FPS > 5% или рост p95 `cpu_frame_ms` > 20% при статусе ≥ `MODERATE` означает «троттлинг есть». Фиксируем, на какой минуте статус впервые стал `LIGHT` и `MODERATE`.
- **Условия прогона (одинаковые каждый раз, пишем в отчёт):** телефон не на зарядке, заряд ≥ 50%, экономия энергии выключена, яркость 50% вручную (автояркость выключена), «Плавный экран» 120 Гц как у Андрея по умолчанию, разрешение экрана в настройках «High» (2244×1008, ADR-0002 §6), без чехла **[или с чехлом, но всегда одинаково]**, телефон лежит на столе, комната 20–25 °C, перед стартом температура батареи ≤ 33 °C (иначе сценарий ждёт и пишет предупреждение), фоновые приложения закрыты, режим полёта или один и тот же Wi-Fi. Между прогонами остывание ≥ 10 мин.

### 5.7 Выгрузка результатов
Сценарий кладёт `qa/result.json`, `perf/*.csv`, `perf/summary.json` (перцентили, посчитанные на телефоне) в общий **отчёт** (§6.5) с `reason=autotest`. На боксе `tests/perf/analyze_frames.py` пересчитывает метрики из CSV, сверяет с `summary.json` и выдаёт таблицу «прошло / не прошло» по §5.4 для `tests/reports/E1-pixel8pro.md`.

## 6. Логи и краши с телефона без adb

### 6.1 Что уже есть в форке (берём за основу, E1-15)
По коду `src/GeneralsZH-Android-Port` (8ef2349):
- `GeneralsMD/Code/Main/AndroidCrashHandler.cpp`: обработчик `SIGSEGV, SIGABRT, SIGBUS, SIGILL, SIGFPE` на `sigaltstack` (переживает переполнение стека), только async-signal-safe вызовы. Пишет в `files/crash.log` (дозапись, прошлая сессия переносится в `crash-prev.log`) PC, LR, адрес ошибки, бэктрейс через `_Unwind_Backtrace`, перевод адресов в «библиотека + смещение» по `/proc/self/maps`, **build id** `libmain.so` и номер запуска CI. Потом вызывает прежний обработчик (`raise`), поэтому системный tombstone тоже создаётся.
- `generals-stderr.log` (+ `-prev.log`) в `getExternalFilesDir`: основной лог движка.
- `LogViewerActivity.java`: просмотр `crash.log` и логов, кнопка **«Поделиться»** через `FileProvider` (файлом, а не текстом), «Копировать», «Очистить».
- Маркеры диагностики (`gx_trace.txt`, `gx_perf.txt`, `gx_net_trace.txt`, …) с переключателями в SetupActivity.

### 6.2 Что добавляем [требования QA к задаче E1-15, реализует Android-платформа]
1. **Кольцевой лог в mmap-файле** `files/qa/ring-<session>.bin` (4 МБ, `MAP_SHARED`). Строки лога движка и лаунчера с меткой времени, потоком и уровнем. Страницы `MAP_SHARED` остаются в page cache после гибели процесса, поэтому хвост лога переживает SIGKILL и OOM (кроме выключения питания). Это замена logcat, которой не нужен adb. На следующем запуске прошлый файл переименовывается в `ring-prev.bin`.
2. **Файл сессий** `files/qa/sessions.json`: последние 20 запусков (id сессии, время старта и конца, версия, `clean_exit`, последняя стадия, последний кадр логики, бэкенд, масштаб). Штатный выход ставит `clean_exit=true`. Если при старте видим `false`, прошлый запуск завершился аварийно.
3. **ApplicationExitInfo** (API 30+, у нас minSdk 29, поэтому с проверкой версии): при каждом старте `getHistoricalProcessExitReasons(pkg, 0, 16)`. Новые записи (по `timestamp`) сохраняем в `exit-info/exit-<ts>.json`: `reason`, `status`, `importance`, `pss`, `rss`, `description`. Для `REASON_ANR` сохраняем трассы потоков (`getTraceInputStream`). Для `REASON_CRASH_NATIVE` на Android 12+ сохраняем **tombstone в protobuf** (`tombstone-<ts>.pb`, схема AOSP `debuggerd/proto/tombstone.proto`; поток может быть `null`, если tombstone уже вытеснен) (https://developer.android.com/reference/android/app/ApplicationExitInfo). `setProcessStateSummary()` при каждой смене стадии кладёт в запись выхода id сессии, стадию и кадр, чтобы связать её с нашим кольцевым логом.
4. **Java-исключения:** `Thread.setDefaultUncaughtExceptionHandler` пишет стек в `crash-java-<ts>.txt` и передаёт исключение дальше системному обработчику.
5. **Сторож зависаний:** нативный поток раз в 1 с сверяет счётчик кадров главного цикла. Нет прогресса 5 с (вне загрузки) → запись `hang` с бэктрейсом главного потока (сигнал `SIGURG`/`SIGUSR2` в поток через `tgkill`, обработчик раскручивает стек) в `crash.log`. Через 30 с в сборках для своих по желанию `abort()` ради tombstone **[предложение QA]**.
6. **Потеря GPU:** проверяем результат `eglSwapBuffers` (`EGL_CONTEXT_LOST`), `glGetGraphicsResetStatus` при наличии `GL_EXT_robustness`/`GL_KHR_robustness`, `VK_ERROR_DEVICE_LOST` в пути DXVK. Пишем событие `gpu_lost` и `device.json`, затем выходим с понятным сообщением (восстановление контекста в Э1 не делаем).
7. **Дамп устройства и GPU** `device.json` (§6.4) при каждом старте рендера, обновляется при смене бэкенда.
8. **logcat своего процесса** по кнопке «Отправить отчёт»: `logcat -d -v threadtime -t 5000` из приложения. Приложение видит только свои строки, и туда попадают сообщения драйвера Mali/PowerVR из нашего процесса **[проверить на Android 14+, поведение READ_LOGS]**.
9. **Символизация на боксе:** CI хранит неурезанные `.so` по build id; `ndk-stack`/`llvm-symbolizer` переводят «библиотека + смещение» из `crash.log` и tombstone в файл и строку (`tests/crash/`, позже).
10. Тестовые кнопки в скрытом меню (сборки для своих): «Тест: SIGSEGV», «Тест: abort», «Тест: зависание 10 с», «Тест: ANR (блок UI-потока 10 с)», «Тест: исключение Java». Сценарий `crash-selftest` проверяет, что каждый тип попал в отчёт.

### 6.3 `device.json`: что собираем
`Build.MANUFACTURER/MODEL/DEVICE/FINGERPRINT`, `Build.SOC_MANUFACTURER/SOC_MODEL` (API 31+), `SDK_INT`, патч безопасности, ОЗУ (`MemoryInfo.totalMem`), размер страницы (`sysconf(_SC_PAGESIZE)`: 4 или 16 КБ), режимы экрана (разрешение, частоты, текущий режим), масштаб рендера и фактический размер поверхности, температурный статус на старте.
GLES: `GL_VENDOR`, `GL_RENDERER`, `GL_VERSION` (содержит версию драйвера Mali/PowerVR), `GL_SHADING_LANGUAGE_VERSION`, список расширений, ключевые лимиты (`MAX_TEXTURE_SIZE`, `MAX_FRAGMENT_UNIFORM_VECTORS`, `MAX_VARYING_VECTORS`, `MAX_SAMPLES`), точность `highp/mediump` во FS (`glGetShaderPrecisionFormat`), выбранный EGL-конфиг, строка форка `[d3d8gles] GLES3 context ready … (s3tc=?)`.
Vulkan (если есть): `apiVersion`, `driverVersion` (с раскодировкой под вендора), `deviceName`, `vendorID/deviceID`, `VkPhysicalDeviceDriverProperties` (`driverID`, `driverName`, `driverInfo`), список расширений.

### 6.4 Экспорт одним файлом
- Кнопка **«Отправить отчёт»** в лаунчере (рядом с просмотром логов форка) и в меню паузы игры.
- **Автопредложение** при старте после аварийного выхода (по `sessions.json` или новой записи `ApplicationExitInfo` с «плохой» причиной): «Прошлый запуск завершился с ошибкой. Отправить отчёт?» Кнопки «Отправить», «Сохранить в файл», «Не сейчас».
- **Отправить** → zip во `files/qa/out/`, затем `ACTION_SEND` с `content://` через `FileProvider` (как «Поделиться» в форке): Telegram, почта, Google Диск и т. п. **Сохранить в файл** → SAF `ACTION_CREATE_DOCUMENT` (`application/zip`), пользователь выбирает «Загрузки» или Диск.
- Перед отправкой экран со **списком файлов и размеров** и галочками для необязательных частей (скриншоты, последний реплей).
- **Позже (Э5):** загрузка на наш сервер (HTTPS POST multipart с инвайт-токеном аккаунта), только по нажатию пользователя. Эндпоинт и хранение (30 дней) — задача «Сети и сервера».
- Лимит размера zip **20 МБ** **[оценка]**: большие логи обрезаются «голова + хвост», как в LogViewerActivity форка, и отметка об обрезке ставится в манифест.

### 6.5 Формат отчёта
Имя: `bfme-report_<versionName>-<versionCode>_<reason>_<YYYYMMDD-HHMMSS>_<session8>.zip` (локальное время телефона, смещение UTC в манифесте).

```
manifest.json            формат отчёта, версия, время, reason (user|crash|anr|hang|gpu_lost|autotest),
                         приложение (versionName/Code, git sha, номер CI, build id libmain.so),
                         устройство (модель, Android), список файлов {path, size, sha256, truncated}
device.json              §6.3
settings.json            бэкенд, масштаб, FPS-кап, нужные ключи Options.ini, включённые маркеры диагностики
sessions.json            последние 20 сессий (§6.2.2)
logs/engine.log          generals-stderr.log текущей или упавшей сессии (+ engine-prev.log)
logs/ring-prev.txt       расшифровка кольцевого лога прошлой сессии (+ ring-current.txt)
logs/launcher.log        лог Java-части
logs/logcat.txt          logcat своего процесса (если удалось)
crash/crash.log          из форка (+ crash-prev.log)
crash/crash-java-*.txt   исключения Java
exit-info/exit-*.json    ApplicationExitInfo
exit-info/tombstone-*.pb native tombstone (Android 12+)
exit-info/anr-*.txt      трассы ANR
qa/result.json           результат сценария (если reason=autotest)
perf/stages.csv, perf/frames.csv, perf/samples.csv, perf/summary.json
replay/last.rep          по галочке: последний реплей (только журнал команд)
screenshots/*.png        по галочке: скриншоты сценария или игры
```
Все JSON содержат поле `"format": "bfme-report/1"`. Кодировка UTF-8, переводы строк `\n`.

### 6.6 Приватность и данные EA
- **Не собираем:** IMEI, серийный номер, `ANDROID_ID`, рекламный ID, номер телефона, контакты, геолокацию, SSID и BSSID Wi-Fi, список установленных приложений.
- **Редактируем:** токены и пароли (как в форке `GXTrace`: маскируется значение, а не вся строка), с Э5 IP-адреса в сетевых логах (оставляем первые два октета) и ники других игроков, если Андрей попросит.
- Пути вида `/storage/emulated/0/...` допустимы. Имя аккаунта Android не пишем.
- **Ничего не уходит с телефона автоматически.** Только по нажатию пользователя и только туда, куда он выбрал сам.
- **Файлы EA в отчёт не попадают:** сборщик берёт файлы только по белому списку путей (`files/qa`, `files/crash*.log`, логи, `perf`, `replay/last.rep`), каталог `GameData/` и `.big` исключены явно, с проверкой расширений перед упаковкой. Скриншоты игры (изображения ресурсов EA) идут только по галочке, на боксе хранятся вне git (`qa-artifacts/`) и никуда дальше не передаются.
- В облачные фермы отчёты с данными игры не попадают (там данных EA нет, `DEVICE-MATRIX.md` §6.1).

## 7. Поток работы со сборкой-кандидатом
1. CI собирает APK (Э0-1…Э0-8 зелёные), прогоняет smoke в эмуляторе (Э0-9) и скриншот-тест (E1-40).
2. QA выпускает **кандидата**, если нет открытых блокеров на ярусах 0–1 и smoke зелёный, и передаёт его Андрею через Оркестратора с коротким чек-листом: что нажать (сценарии §5) и что прислать (отчёты).
3. Андрей прогоняет чек-лист (≈ 40 мин на полный протокол Э1-2б, ≈ 15 мин на perf-run), присылает zip-файлы.
4. QA разбирает отчёты на боксе (символизация, `analyze_frames.py`), пишет `tests/reports/<веха>-pixel8pro.md` и заводит дефекты (§3.4). Блокеры сразу уходят владельцу области и Лиду.
