# ADR-NET-001: стек сервера (лобби, сигналинг, релей)

- Статус: **предложено**
- Дата: 02.10.2026
- Автор: «Сеть и сервер»
- Утверждают: Лид движка, Оркестратор, Андрей

## Контекст
Нужны REST + WebSocket (аккаунты по инвайтам, лобби, квикматч, ICE-сигналинг для GNS), UDP-релей с WS-fallback, STUN/TURN, SQLite и реплеи. Один небольшой VPS, 5–30 пользователей. Клиент — C++ (форк MYSOREZ, GPL v3), protobuf уже в его зависимостях (vcpkg-порт GNS: openssl, protobuf). Операционные силы — агенты команды, без отдельного DevOps.

## Варианты
1. **Go 1.2x.**
   - Статический бинарник, образ distroless ~10–20 МБ [оценка].
   - Concurrent GC: типичные STW-паузы меньше миллисекунды (go.dev/doc/gc-guide, go.dev/blog/ismmkeynote).
   - net/netip, пулы буферов для релея; pion/turn и pion/stun (MIT, RFC 5389/5766/6062/6156) — STUN/TURN можно встроить в релей с той же авторизацией по билету.
   - WS: coder/websocket или gorilla; SQLite — modernc.org/sqlite (без CGO).
2. **C# / .NET 8+.**
   - Kestrel и WebSockets отличные; productive язык; GeneralsOnline Services на C# (переиспользовать нельзя: лицензия [не проверено] и чужой протокол).
   - Рантайм тяжелее (образ ~100–200 МБ, RAM 50–100 МБ на сервис [оценка]); паузы server GC обычно единицы мс [оценка].
   - Зрелого чистого .NET TURN-сервера нет [не проверено], так что всё равно нужен coturn.
3. C++ (общий код с клиентом) — отвергнут: дорого в разработке и безопасности ради отсутствующей выгоды. Общий протокол даёт protobuf, а не общий код.

## Решение (предлагается)
Go для bfme-api и bfme-relay; coturn для TURN в фазе 1 (позже, возможно, pion/turn внутри релея); SQLite (WAL) с переносимым SQL; protobuf — общая схема WS- и релей-сообщений для C++ и Go; Docker Compose на одном VPS.

## Обоснование
- Производительность релея: нагрузка ≤ ~10 тыс. пакетов/с (SERVER-ARCH §9) — оба стека справятся; решают паузы и простота. Паузы GC Go (<1 мс) несущественны при бюджете RA ~200 мс.
- Деплой: один бинарник, маленький образ, мало RAM — подходит для VPS на 2–4 ГБ.
- Сеть: экосистема pion (STUN/TURN/ICE) на Go, нужная для сигналинга, TURN и диагностики.
- Компетенции: оба языка доступны агентам; Go проще читать и ревьюить и даёт меньше вариативности.
- Переиспользование с клиентом C++: не зависит от языка; protobuf уже есть в клиенте.

## Последствия
- Нужен генератор protobuf для C++ и Go в CI; схемы версионировать (`proto_ver`).
- Переход на Postgres — при росте или нескольких инстансах; миграции goose.
- Пересмотреть решение, если появится нужда в headless-проверке реплеев движком (C++ процесс, вызывается из Go как подпроцесс — на решение не влияет).
