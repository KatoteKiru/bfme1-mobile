## 2026-10-16: E1-52 Teams, PlayerScriptsList, BuildLists, ScriptGroup v3

BFME1 `.map` files put `Teams`, `PlayerScriptsList` and `BuildLists` next to
`SidesList`. The logical loader never registered them, so `DataChunkInput`

`ERROR_CORRUPT_FILE_FORMAT` before any field is written. Zero Hour versions
stay on the old path: ScriptGroup v1 has no subroutine byte, v2 and v3 do,
and nested groups are registered only for v3.

An action or condition whose name is not a Zero Hour template is stored,

## 2026-10-16: BlendTileData counts follow the chunk, not 4096/65536/131072

The Trilogy (Updated) Singleplayer (`_patch222maps.big`) dies in
`WorldHeightMap::ParseBlendTileData` with `ERROR_CORRUPT_FILE_FORMAT`. The
three counts are checked against `NUM_SOURCE_TILES` / `NUM_BLEND_TILES` /
`NUM_CLIFF_INFO` (4096 / 65536 / 131072). E1-25 already sizes the tile, blend
and cliff tables from those counts, so the constants were only a garbage
ceiling, and this map is past them.

The loader now rejects a count when it is negative, above a garbage ceiling
(262144 bitmap tiles, 1048576 blends, 1048576 cliffs), or when the blend and
cliff records still to be read do not fit in `dataLeft`. Blend records are
13, 14 or 18 bytes by version; cliff records are 38 bytes from v5; index 0 of
each table is not in the file. Bitmap tiles are not records in the chunk, so
only the ceiling applies to them, and to `numEdgeTiles` and to where a
texture class ends. The failure line names the three counts, `dataLeft`, and
how many bytes the blend and cliff records need. It goes to `DEBUG_LOG` and
to stderr.

The old constants stay. WorldBuilder still has fixed arrays of those sizes
(`TBlendTileInfo blendInfo[NUM_BLEND_TILES]` and the source-tile loops). The
game tables are heap pointers sized by the map. The atlas packer uses a
`std::vector` grid of page slots, not `NUM_SOURCE_TILES`. `NUM_TEXTURE_CLASSES`
is still 256 class headers. `tests/blend` loads a synthetic chunk one past
each old limit, and rejects a count whose records are not in the chunk. Those
tests ignore `[chunk] skipped` lines from the chunk walker. The gamedata
cases still skip unless `BFME_GAMEDATA` is set.

## 2026-10-16: PolygonTriggers v5

BFME maps store PolygonTriggers at version 5. The Zero Hour reader stopped
at riverStart and took the next four bytes as `numPoints`. On Fords of Isen
those bytes are the start of `TWWater01.tga` (1465122829), and the following
`new[]` asked for about 17.6 GB.

Version 5 now reads the six texture names, the additive byte, RGB plus the
pad byte, uv scroll and alpha, then the points. `numPoints` has to fit in the
bytes still in the chunk (12 bytes per point) or the parser logs and throws
before it allocates. After those fields the parser also rejects a chunk whose
remainder is already past the end or shorter than the point count: a release
build does not check that inside `readAsciiString`. Versions above 5 are
rejected the same way, and that path clears triggers already loaded so a
failed map does not keep the previous one. Versions 1–4 still follow the Zero
Hour layout, including the default water area on v1. The fields are stored
for the water renderer; this change does not draw them. The writer still
emits version 4 and drops the water fields; that is a TODO pointing at E1-29
in `docs/E1-BACKLOG.md`.

## 2026-10-16: K6 headless device gate and llvmpipe texture edge

Headless died in `W3DSnowManager::ReAcquireResources` because
`DX8IndexBufferClass` reads `DX8Wrapper::Get_Current_Caps()` and headless
never calls `WW3D::Init`. The same gate now covers the other
`ReAcquireResources` paths map load reaches (water, tracks, shadows, shroud,
smudge, shader init).

The 4096 texture-edge clamp applies only when the device name is llvmpipe,
lavapipe, softpipe or swrast, and never under `__ANDROID__`. Mali keeps the
edge GL reports (often 8192). The 128 MiB GLES shadow check is a guard: a
full 4096² chain is ~85 MiB, so it does not reject a legal texture, and it
is skipped when the adopted edge is larger.

Windowed lavapipe under Xvfb still aborts inside LLVM at DXVK device
creation (`LLVM ERROR: out of memory` / `Buffer allocation failed`, RSS
~75 MiB). The caps clamp runs only after that device exists, so it does
not address this. `LP_NUM_THREADS` defaults to 2 when unset; that is not
that abort.

## 2026-10-08: E1-51 terrain atlas 4096×2048, pages of 2048

The ZH packer fits 784 tiles on one 2048² page and drops the rest at the first
free cell of a row. Fords of Isen (984 tiles) loses 17 classes that way.
Trilogy is 3396 tiles, which does not fit in 4096² either (3136 slots).

page, so a side of 15 or more takes a whole 2048 page (Eastfold 4, Trilogy 5).

the blend anomalies: 16 detail lines, then a summary. Cliff u/v stay local
class units (1 is one class edge, no wrap). `getCliffClassInfo` returns the

`origin + fract(local) * size`. `getUVForNdx` and `getUVForBlend` also return
the page. Atlas mipmaps stop at 3 levels so trilinear filtering does not blend
across the 4px border. The path follows the queried max texture size, which
`FillCaps` reports. `CreateTexture` returns `D3DERR_INVALIDCALL`,
`D3DERR_NOTAVAILABLE` or `D3DERR_OUTOFVIDEOMEMORY` instead of always succeeding.

Synthetic tests cover Fords, Eastfold and Trilogy. The 115 real maps are still
for the team machine.

## 2026-10-08: logic-thread FP gate (ADR-0003 §2.3)

`fp::bindLogicThread()` is the first call in `GameMain()`, before the engine
init. `GameLogic::init` and `setFPMode()` compare `std::thread::id`. Debug and
CI abort on a mismatch or on a check that happened before the bind. Release
logs once; if nothing was bound yet, that log is followed by binding the
caller. A second bind from another thread aborts only in debug. The Android
debug thread-name check warns when the name is not `SDLThread` and does not
abort. `gettid()` is only in the log line.

`setFPMode()` is a wrapper over `fp::reset()`. The stub's `reset()` is the
previous non-VC6 body (`fesetenv`, `feclearexcept`, `fesetround(FE_TONEAREST)`,
and on x86 the x87 control word and MXCSR nearest). `read()` and
`isExpected()` stay trivial until Platform replaces the file. VC6 still
compiles the old `setFPMode()` in place. `g_mode` is `std::atomic` and is
read and written with relaxed ordering.
