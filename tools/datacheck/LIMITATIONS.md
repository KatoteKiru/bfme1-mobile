
## Известные ограничения

- **Схема OpenSAGE извлекается статически** (regex + сопоставление скобок по C#, без компилятора). Поле считается блоком, если его парсер (с рекурсией до 5 уровней по вызовам методов) вызывает `ParseBlock/ParseNamedBlock/ParseIndexedBlock/ParseTopLevelBlock/ParseBlockContent`; модулем, если вызывает `ParseModule(parser, XxxParseTable)`. Ветки `if (parser.SageGame == CncGenerals...)` отбрасываются в пользу BFME-пути. Поля вида `AddEmotion = X` (строка) / `AddEmotion = TYPE X ... END` (блок) различаются по числу токенов (`min_values`).
- **Метка игры** — только `[AddedIn(SageGame.X)]` на свойстве/классе. Непомеченное в OpenSAGE считается «есть с Generals», поэтому список BFME-only по OpenSAGE — нижняя оценка. Второй, более надёжный критерий — отсутствие имени в C++ коде Generals ZH (GeneralsGameCode: `theTypeTable`, `addModule`, все таблицы `FieldParse`). Имена полей ZH сравниваются **глобально** (не по блоку): поле, которое в ZH есть в другом блоке, будет считаться «известным».
- **Значения не типизируются**: парсер проверяет структуру (блоки/поля/модули), а не типы и диапазоны значений. Ссылки на другие ассеты (Weapon, FXList, OCL...) не проверяются на существование.
- **Неизвестные блоки** пропускаются эвристикой глубины: строка без `=` или строка, за которой идёт более глубокий отступ, открывает вложенный блок до `END`. Ошибка эвристики видна как структурное предупреждение (`stray END` / `not closed`); при 0 предупреждений структура сошлась.
- **BeginScript … EndScript** (встроенный Lua) читается как сырой текст до первой строки, где первый токен `EndScript` (без учёта регистра); иначе Lua-`end` закрывал бы блоки. Побайтное тело блока даёт `syntax.lua_blocks`; в records анализатора текст Lua нормализован (комментарии и пробелы), для контракта брать `syntax.lua_blocks`/`beginscript_blocks.tsv`.
- **#define**: собираются со всех INI до разбора (глобально, первое определение выигрывает), подставляются только в значения для диффа. `#include` поддерживается (относительно каталога файла, `..`), в данных BFME1 1.03 не встречается.
- **Наследование объектов**: семантика OpenSAGE `AddModuleData` / Generals `copiedFromDefault` (наследованные модули того же слота удаляются при добавлении модуля с пересекающимися ModuleKinds; `InheritableModule` не удаляется; `RemoveModule/ReplaceModule` по тегу). `ModuleKinds` берётся из OpenSAGE; у модулей без ModuleKinds (напр. HordeContain) наследованная копия не вытесняется. Объекты из map.ini в итоговую частоту не входят.
- **Приоритет архивов** как в движке SAGE (EA/GeneralsGameCode): loose-файлы > архивы; архивы в порядке `_stricmp` полного относительного пути, **первый выигрывает** (`_patch222*.big` раньше `ini.big`). OpenSAGE делает наоборот (последний выигрывает) — для BFME-патчей это дало бы неверный итог. Как BFME1 обрабатывает `.big` в подкаталогах (lang\ и т.п.) — не проверено на исполняемом файле, принято как в Generals (рекурсивно).
- **Кодировка** INI: latin-1 (байт-в-байт), локализованные `*9x.ini` не подменяются.
- **Дифф патча** сопоставляет поля по пути блоков (тип+имя блока, заголовки вложенных блоков, тег модуля) и порядковому номеру повторяющегося поля в блоке; перестановка повторяющихся полей (например, нескольких `Prerequisites/Object`) покажется как изменение. Числа сравниваются после нормализации (`380.0 == 380`, `50% == 0.5`, `1.5s == 1500`), локаль не влияет (Decimal по тексту).

### Скирмиш-граф и механики (gameplay.md)
- Раскладки крепостей и лагерей (`Camp_*`, `Castle_*`, `Farm_Gondor` и т.п. из `CastleToUnpackForFaction`) — не INI-объекты, а `bases\<имя>\<имя>.bse` (DataChunk, как `.map`). В базе (`ini.big`+`maps.big`) их нет, они есть только в `_patch222bases.big`. Поэтому в отчёте по базе (`out/`) то, что стоит в лагере изначально (цитадель, рабочие), попадает в граф только через участки, флаги и строителей. В `out-all/` объекты из .bse берутся эвристикой: идентификаторы в распакованном файле, совпадающие с именами объектов; полноценного разбора ObjectsList пока нет.
- Не прослеживаются: спавн через OCL, призыв заклинаниями (SpellBook / SpecialPower). Объекты на картах считаются отдельно (`map_content.md`), в граф скирмиша не входят.
- Классы определяются по KindOf (HERO / STRUCTURE / HORDE / INFANTRY|CAVALRY|MONSTER|…). Объекты с другим `Side` отбрасываются, кроме героев из BuildableHeroesMP.
- Поиск механик идёт по шаблонам в тексте. Если механика зашита в движке (game.dat), а не в INI, данные её не покажут. Так обстоит дело с падением дохода фермы от соседей: в базе для этого нет ни одного поля.

### Счётчики карт (maps.md)
- Считаются по итоговым `.map` (в `out/` 115 карт `maps\`, в `out-all/` ещё `libraries\` и `bases\` из патча). Определения — в docstring `datacheck/maps.py`. Индекс 0 у blend/3-way/cliff означает «нет» и висячим не считается.
- Семантика флагов вне `&0x3` и `customBlendEdgeClass` при нуле классов неизвестна (в OpenSAGE это TODO). Отчёт только считает, где они встречаются.

### Карты 1v1 и скрипты (map_content.md)
- 1v1 = ровно 2 стартовые позиции (`Player_1_Start`, `Player_2_Start` подряд, как в ZH) + `isMultiplayer = yes` и `isOfficial = yes` в `maps\mapcache.ini`. Число игроков берётся из самой карты: fileSize в кэше 2.22 расходится с файлами у большинства карт, хотя numPlayers совпадает у всех карт, которые есть в кэше.
- Имена скриптов ищутся эвристическим обходом подчанков (`probe.walk`), как и для `docs/formats/data/…tsv`. Полный разбор Script/ScriptGroup не сделан. На картах базы результат совпадает с TSV из docs побайтно.
- «Ресурсы»: участки застройки (KindOf BASE_SITE/BASE_FOUNDATION/BASE_DEFENSE_FOUNDATION), логова (итоговый объект с `SpawnBehavior`) и классы текстур рельефа. Доход от ферм и прочего на карте не моделируется.
- Точки дорог (флаги FLAG_ROAD_POINT1/2) в частоты объектов не входят.

### Эталон (reference/)
- Поля объекта — это ключи верхнего уровня блока Object/ChildObject/ObjectReskin (включая вложенные блоки вроде ArmorSet и неизвестные ключи, без строк модулей и AddModule/ReplaceModule/RemoveModule). После наследования их число равно объединению множеств родителя и потомка: повторный ключ у потомка не добавляется второй раз. У повторяющихся ключей (несколько `ArmorSet`) учитывается одно имя. Plain Object наследует от DefaultThingTemplate, как в resolve().
- Объекты из map.ini разрешаются поверх data\ini своей карты. `Object X` в map.ini считается новым определением, а не правкой глобального X. Как это делает движок BFME, не проверено.
- `nested_openers.tsv` описывает правила нашего анализатора (схема OpenSAGE плюс эвристика), а не правила движка BFME.

### Синтаксис против ZH (раздел 8)
- Поведение ZH взято из чтения `repo/` (Core/GameEngine/Source/Common/INI/INI.cpp и др.) для release-сборки, где DEBUG_CRASH ничего не делает. На устройстве не проверялось.
- «Нет в ZH» для полей и вложенных блоков считается по глобальному списку имён полей ZH, поэтому это нижняя оценка. Макросы ищутся по словам в значении.

### Дифф патча
- Ключ блока — тип + имя. Если патч сменил тип (`Object` ↔ `ChildObject`), это пара «удалён + добавлен». Вложенные поля без имени нумеруются по порядку внутри блока: вставка поля в середину даёт каскад «changed» по тому же полю ниже по порядку.
- `map.ini` сравниваются пофайлово, `data\ini` — глобально.

### PRODUCTION % (раздел 9 report.md)
- Как читается `%` (`modifiers.hypothesis`), выведено только из данных: из комментариев к записям и из того, слит `%` с числом или нет. Это **не подтверждено, ждёт замера в игре**. OpenSAGE всегда делит на 100 (`IniParser.cs` ParsePercentage), и для записей вида `X %` это расходится с комментариями в данных. Как PRODUCTION применяется к доходу (умножение), видно только по OpenSAGE (`ModifierList.cs`, `AutoDepositUpdate.cs`).
